# Исправление найденных дефектов и улучшение существующего кода

**Дата:** 2026-08-28
**Ветка:** feature/redesign
**Источник списка:** сводка в конце [главы 08 гайда](../../guide/08-configuration-and-running.md)

## Цель

Закрыть все дефекты, найденные при написании гайда, и подтянуть качество существующего кода
до состояния, в котором на него не стыдно смотреть на собеседовании. Новую функциональность
не добавляем.

## Что НЕ входит (отдельные этапы дорожной карты)

- агент и мульти-сервер;
- heartbeat-алерты (детект «узел не отвечает»);
- аутентификация API и вход в веб-интерфейс;
- retention и прореживание истории;
- webhook-канал оповещений, уровни warning/critical.

## Что входит

### Раунд 1 — безопасность

| # | Проблема | Решение |
|---|----------|---------|
| 1.1 | Пароль от БД в `appsettings.json` под git | строку подключения перенести в User Secrets, в файле оставить шаблон без пароля |
| 1.2 | Бот отвечает любому собеседнику | сверять `message.Chat.Id` с настроенным `Telegram:ChatId` |

Пароль уже попал в историю git — это исправляется отдельно и требует решения пользователя
(смена пароля в БД обязательна, переписывание истории — по желанию).

### Раунд 2 — корректность

| # | Проблема | Решение |
|---|----------|---------|
| 2.1 | `double.Parse` без инвариантной культуры при разборе `/proc` | `CultureInfo.InvariantCulture` во всех разборах; заодно вынести парсеры в чистые функции |
| 2.2 | CPU в Windows: перебор всех процессов, занижение, дороговизна | `GetSystemTimes` из `kernel32.dll` — прямой аналог `/proc/stat` |
| 2.3 | Диск выбирается «первый попавшийся» | брать раздел, на котором стоит система |
| 2.4 | `async void` без `try/catch` в `TopNav` | обернуть тело в `try/catch` с логированием |
| 2.5 | Обращения по индексу без проверки длины в парсерах | явные проверки с понятным сообщением об ошибке |

### Раунд 3 — данные и производительность

| # | Проблема | Решение |
|---|----------|---------|
| 3.1 | Нет индекса по `TimestampUtc` | `HasIndex` в `OnModelCreating` + миграция |
| 3.2 | Синхронные обращения к БД в фоновых сервисах | везде `...Async` с передачей токена |
| 3.3 | Лишний трекинг в запросах только на чтение | `AsNoTracking()` |

### Раунд 4 — чистота кода

| # | Проблема | Решение |
|---|----------|---------|
| 4.1 | `GetLatest` отдаёт сущность наружу и никем не используется | удалить эндпоинт (его функциональность полностью покрывает `/status`) |
| 4.2 | Формула процентов продублирована в контроллере и боте | вычисляемые свойства в `MetricSnapshot`, `Ignore` в `OnModelCreating` |
| 4.3 | Строки вместо перечислений в типах алертов | `enum MetricKind`, `enum AlertKind` + конвертер значений EF (в базе остаются строки) |
| 4.4 | Интервалы сбора и проверки зашиты в код | `MonitoringOptions` через `IOptions<T>` и секцию `Monitoring` в конфигурации |

### Раунд 5 — надёжность алертинга (улучшение существующего)

| # | Проблема | Решение |
|---|----------|---------|
| 5.1 | Состояние алертов теряется при перезапуске | восстанавливать из последних записей таблицы `Alerts` при старте |
| 5.2 | Дребезг на границе порога | срабатывать только после N подряд превышений (N из конфигурации) |
| 5.3 | Состояние трёх метрик через `Func`/`Action` | заменить на словарь состояний по типу метрики |

### Раунд 6 — тесты

Проект `ServerMonitor.Tests` (xUnit) с юнит-тестами на:

- разбор `/proc/meminfo`, `/proc/uptime`, `/proc/stat` (включая проверку инвариантной
  культуры и повреждённых входных данных);
- вычисление процента загрузки CPU по двум замерам;
- вычисляемые свойства `MetricSnapshot`;
- логику подтверждения превышения порога.

### Раунд 7 — синхронизация гайда

Главы 02, 03, 04, 05, 07, 08 описывают код, который изменится. После каждого раунда правок
соответствующие разделы гайда приводятся в соответствие, а сводный список в конце главы 08
переписывается: исправленное убирается, остаётся только то, что относится к будущим этапам.
Добавляется глава 09 с разбором сделанных исправлений — что было, почему плохо, как стало.

## Инварианты

- Публичный контракт API не меняется, кроме удаления неиспользуемого `GET /api/metrics/latest`.
- Формат данных в базе остаётся совместимым: типы алертов продолжают храниться строками.
- Внешний вид интерфейса не меняется.
- После каждого раунда: `dotnet build` без ошибок и предупреждений, запуск и проверка в
  браузере, отдельный коммит.

## Критерии готовности

- Все пункты списка из главы 08, кроме отнесённых к будущим этапам, закрыты.
- Тесты проходят (`dotnet test`).
- Гайд не противоречит коду.
- Секретов в отслеживаемых git файлах нет.
