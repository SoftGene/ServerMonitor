# Упаковка — концепция и план

**Дата:** 2026-09-08
**Ветка:** feature/packaging
**Этап дорожной карты:** 4 из 5

> Спека и план в одном документе: этап небольшой, а разносить их по двум файлам ради ритуала
> смысла нет.

## Цель

Сейчас, чтобы запустить проект, нужны .NET 10 SDK, Postgres, три команды `dotnet user-secrets`,
ручная миграция и три терминала. Человек, открывший репозиторий, до работающей системы не
дойдёт.

После этапа:

```bash
cp .env.example .env   # вписать пароль и два секрета
docker compose up -d
```

Плюс `/healthz` — он нужен не только для красоты: система принципиально не может сообщить о
падении самой себя (глава 11), и внешнему наблюдателю нужна точка, которую он будет опрашивать.

## Принятые решения

| Вопрос | Решение | Обоснование |
|--------|---------|-------------|
| Что в compose | postgres, api, web | это сервер; агент ставится на наблюдаемую машину |
| Агент в контейнере | **Dockerfile есть, в compose нет** | см. ниже — контейнер измерил бы сам себя |
| Миграции | **применяются при старте API** | «одна команда» иначе не работает |
| TLS | **внутри контейнеров только HTTP** | сертификаты — забота обратного прокси |
| Секреты | через `.env` и переменные окружения | User Secrets в контейнере не существует |
| `/healthz` | **без аутентификации** | проверку, требующую секрет, внешний наблюдатель не сделает |

### Почему агента нет в compose

Ловушка, на которой легко обжечься: **агент в контейнере измеряет контейнер, а не хост.**
Память ограничена cgroup, диск — это слой образа, а не диск машины. Получились бы правдоподобные
и неверные цифры — худший вид ошибки в мониторинге.

Чтобы агент в контейнере видел хост, нужны `--pid=host`, монтирование `/proc` и `/` только для
чтения, и всё равно остаются оговорки. Поэтому по умолчанию агент ставится на машину как
обычная программа или юнит systemd, а Dockerfile для него оставляем — он пригодится тому, кто
понимает, что делает.

### Почему миграции при старте — и когда так нельзя

`dbContext.Database.MigrateAsync()` при запуске API. Иначе обещание «одна команда» ломается:
после `docker compose up` человек упирается в пустую базу.

> **Когда так делать нельзя.** Если экземпляров API несколько, при одновременном старте они
> начнут применять миграции наперегонки. Тогда миграции выносят в отдельный шаг развёртывания —
> отдельный контейнер или задачу CI. Здесь экземпляр один, и это осознанное упрощение, а не
> незнание.

## Шаги

- [ ] **1. `/healthz`**

Минимальный эндпоинт: проверяет, что база отвечает. `200` с телом `healthy`, `503` с телом
`unhealthy` — без подробностей: наружу не должно уходить, что именно сломалось.
Регистрируется до `MapControllers`, аутентификации не требует.

- [ ] **2. Миграции при старте**

В `Program.cs` после `builder.Build()`, в отдельном scope, с логом.

- [ ] **3. Dockerfile для Api, Web, Agent**

Многоступенчатая сборка: `sdk` собирает, `aspnet` (для агента — `runtime`) выполняет.
Контекст сборки — корень репозитория, потому что проекты ссылаются друг на друга.
Запуск не от root.

- [ ] **4. `.dockerignore`**

Без него в контекст сборки уедут `bin`, `obj`, `.git` и `.vs` — это сотни мегабайт и риск
затащить в образ чужие артефакты.

- [ ] **5. compose: postgres + api + web**

- api зависит от postgres с проверкой готовности (`healthcheck`), иначе он стартует раньше базы;
- web зависит от api;
- секреты и адреса — через переменные окружения;
- порты наружу: web `5298`, api `7212` (для агентов и curl).

- [ ] **6. `.env.example`**

Три значения: пароль базы, enrollment-токен, служебный ключ. С командами генерации.

- [ ] **7. Проверка**

`docker compose up -d --build` на чистой базе (отдельный том), затем:
открыть интерфейс, пройти первичную настройку, зарегистрировать агента с хоста, убедиться, что
замеры идут. Проверить `/healthz` при живой и остановленной базе.

- [ ] **8. README**

Раздел «Quick start» с одной командой — выше текущего раздела для разработки.

- [ ] **9. Глава 13 гайда**

Разделы: зачем упаковка; многоступенчатая сборка и почему контекст — корень; почему агент не в
compose (измерил бы себя); миграции при старте и когда так нельзя; healthcheck и порядок
запуска; почему `/healthz` без аутентификации и почему без подробностей; TLS как забота прокси.

## Границы

**Не входит:** публикация образов в реестр, CI-сборка, Kubernetes, обратный прокси с TLS,
retention (этап 5, решено не делать — ограничение остаётся названным в README).
