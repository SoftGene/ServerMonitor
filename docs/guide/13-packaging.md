# Глава 13 — Упаковка

До этого этапа, чтобы запустить проект, требовались .NET 10 SDK, Postgres, три команды
`dotnet user-secrets`, ручная миграция и три терминала. Человек, открывший репозиторий из
любопытства, до работающей системы не доходил.

Теперь так:

```bash
cp .env.example .env
docker compose up -d
```

Глава — о том, что для этого понадобилось, и о нескольких решениях, которые кажутся
техническими мелочами, а на деле определяют, будут ли цифры на экране правдой.

---

## Часть 1. Зачем это вообще

Причина не в удобстве, а в **воспроизводимости**.

«Работает у меня на машине» — не свойство программы, а свойство машины. На ней стоит нужный
SDK, нужная версия Postgres, в User Secrets лежат нужные значения. Ничего из этого нет у того,
кто клонирует репозиторий, и ничего из этого нет на сервере.

Контейнер описывает окружение **кодом**: какой образ, какие переменные, какие порты, кто кого
ждёт. Файл `docker-compose.yml` — это не скрипт запуска, а описание системы целиком.

> **Побочная выгода, которая для тебя сейчас важнее прочих.** Инженер, открывший твой
> репозиторий, почти наверняка попробует `docker compose up`. Если это работает — он видел
> систему живьём. Если нет — он закрыл вкладку.

## Часть 2. Многоступенчатая сборка

[`ServerMonitor.Api/Dockerfile`](../../ServerMonitor.Api/Dockerfile) состоит из двух этапов:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
...
RUN dotnet publish ... -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
COPY --from=build /app .
```

Первый этап собирает, второй — выполняет. В итоговый образ попадает только результат `publish`.

> **Почему так.** Образ SDK весит около гигабайта: в нём компилятор, NuGet, инструменты. Для
> **запуска** приложения ничего этого не нужно — нужна только среда выполнения. Одноступенчатая
> сборка тащила бы на сервер компилятор, который там никогда не понадобится, и заодно
> увеличивала бы поверхность атаки.

### 2.1. Порядок COPY — не косметика

```dockerfile
COPY ServerMonitor.Domain/*.csproj ServerMonitor.Domain/
COPY ServerMonitor.Infrastructure/*.csproj ServerMonitor.Infrastructure/
COPY ServerMonitor.Api/*.csproj ServerMonitor.Api/
RUN dotnet restore ...

COPY ServerMonitor.Domain/ ServerMonitor.Domain/
...
```

Сначала копируются **только файлы проектов**, потом делается `restore`, и лишь затем копируется
исходный код.

> **Зачем.** Docker кэширует каждый слой и переиспользует его, пока не изменились входные
> данные. Пакеты зависят только от `.csproj`. Если скопировать сразу всё, любая правка одной
> строки кода делала бы слой с `restore` недействительным, и все пакеты качались бы заново —
> каждую сборку.
>
> Это общий приём: **сначала то, что меняется редко, потом то, что меняется часто.**

### 2.2. Контекст сборки — корень репозитория

```yaml
build:
  context: .
  dockerfile: ServerMonitor.Api/Dockerfile
```

Контекст — это то, что Docker вообще может скопировать. Проекты ссылаются друг на друга
(`Api → Infrastructure → Domain`), поэтому контекстом обязан быть корень: из папки
`ServerMonitor.Api/` соседние проекты не видны.

Отсюда же необходимость [`.dockerignore`](../../.dockerignore): без него в контекст уедут `bin`,
`obj`, `.git` и `.vs` — сотни мегабайт, которые нужно передать демону Docker при каждой сборке.
И, что важнее, чужие артефакты могли бы попасть в образ.

```
**/bin/
**/obj/
.git/
.env
**/appsettings.Development.json
```

Обрати внимание на последние две строки: локальные секреты в образ не попадают никогда.

## Часть 3. Решение, от которого зависит правдивость цифр

Самое важное в этой главе.

**Агента нет в `docker-compose.yml`**, хотя Dockerfile для него написан.

> **Почему.** Агент в контейнере измеряет **контейнер, а не хост**. Память ограничена cgroup,
> «диск» — это слой образа, а не диск машины. Загрузка процессора формально видна хостовая, но
> вместе с двумя неверными числами она создаёт полную иллюзию работающего мониторинга.
>
> Получились бы **правдоподобные и неверные** цифры. Это худший вид ошибки в мониторинге:
> неработающий мониторинг заметен сразу, а врущий — нет. Ты смотришь на «памяти занято 40%» и
> спокоен, а на машине давно кончилась память.

Чтобы агент из контейнера видел хост, нужны `--pid=host`, монтирование `/proc` только для
чтения, и всё равно остаются оговорки. Поэтому по умолчанию агент ставится на наблюдаемую
машину обычной программой, а Dockerfile оставлен тому, кто понимает, что делает — и в нём
об этом написано прямым текстом.

> **Правило шире мониторинга.** Если инструмент измеряет окружение, спрашивай: **чьё именно
> окружение он сейчас видит?** Профилировщик внутри контейнера, тест производительности в
> виртуалке, замер сети из другой подсети — та же ловушка.

## Часть 4. Порядок запуска

```yaml
depends_on:
  postgres:
    condition: service_healthy
```

Наивное `depends_on: [postgres]` означает лишь «запусти контейнер базы раньше». Но Postgres
начинает принимать соединения через несколько секунд после старта процесса, и API, стартовав
первым, упал бы на миграциях.

Поэтому у базы есть проверка готовности:

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U monitor -d servermonitor"]
  interval: 5s
  retries: 10
```

и API ждёт именно её.

> **Мысль.** «Контейнер запущен» и «сервис готов принимать работу» — разные события, и между
> ними секунды. Эта разница ломает системы регулярно; в распределённых системах она же
> заставляет писать повторы с выдержкой (глава 10).

## Часть 5. Миграции при старте

```csharp
using (var scope = app.Services.CreateScope())
{
    var dbContext = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    await dbContext.Database.MigrateAsync();
}
```

Без этого обещание «одна команда» ломается: после `docker compose up` человек упирается в
пустую базу и сообщение об отсутствующих таблицах.

> **Когда так делать нельзя — и это важнее самого приёма.** Если экземпляров API несколько,
> при одновременном старте они начнут применять миграции наперегонки. Кто-то упадёт, а в худшем
> случае схема останется в промежуточном состоянии.
>
> В таких системах миграции выносят в **отдельный шаг развёртывания**: отдельный контейнер,
> задача CI или ручная команда перед выкаткой. Здесь экземпляр один, и это осознанное
> упрощение, записанное в комментарии рядом с кодом.

Обрати внимание на `CreateScope()`: `AppDbContext` зарегистрирован как scoped, а на старте
приложения области запроса ещё нет. Тот же приём, что в фоновых сервисах (глава 04).

## Часть 6. `/healthz`

```csharp
app.MapGet("/healthz", async (AppDbContext dbContext) =>
    await dbContext.Database.CanConnectAsync()
        ? Results.Text("healthy")
        : Results.Text("unhealthy", statusCode: StatusCodes.Status503ServiceUnavailable));
```

Три решения в четырёх строках.

**Проверяет базу, а не только себя.** Ответ «я жив» от процесса, который не может достучаться
до базы, бесполезен: с точки зрения пользователя система не работает.

**Без аутентификации.** Проверку, требующую секрет, внешний uptime-сервис выполнить не сможет —
а он и есть главный потребитель этой точки. Здесь нечего защищать: она не отдаёт данных.

**Без подробностей.** Наружу уходит `healthy` или `unhealthy`, без текста исключения и имени
хоста базы. Диагностика — в логах, где её видит владелец сервера.

> **Зачем эта точка вообще.** В главе 11 мы упёрлись в то, что система **принципиально не может
> сообщить о собственной смерти**: некому выполнить проверку и некому отправить сообщение.
> Единственное решение — внешний наблюдатель. `/healthz` — это то, что он будет опрашивать.
>
> Сам наблюдатель в проект не входит и не должен: он обязан быть отдельной системой, иначе
> вопрос просто сдвигается на уровень выше.

## Часть 7. TLS и секреты

**Внутри контейнеров только HTTP.** Возиться с сертификатами внутри сети compose незачем:
шифрование — забота обратного прокси (nginx, Caddy, Traefik), который стоит перед системой и
терминирует TLS. Сервисы за ним общаются по имени: `http://api:8080`.

**Секреты — переменными окружения.** User Secrets в контейнере не существует: это механизм для
машины разработчика, хранящий значения в профиле пользователя. В compose их место — `.env`,
который в `.gitignore`, а в репозитории лежит `.env.example` с пустыми значениями.

Обязательность проверяется синтаксисом самого compose:

```yaml
Api__ServiceKey: ${SERVICE_KEY:?set SERVICE_KEY in .env}
```

Двоеточие с вопросительным знаком означает «без этой переменной не запускаться». При проверке
это сработало сразу: compose отказался стартовать, пока переменные не были заданы, — вместо
того чтобы поднять систему с пустым ключом.

> Та же мысль, что в главе 12: **отсутствие настройки безопасности — это отказ, а не
> разрешение.** Здесь она выражена одним символом в файле конфигурации.

Обрати внимание на двойное подчёркивание в `Api__ServiceKey`. Конфигурация .NET иерархична, и
в переменных окружения разделителем уровней служит `__`, потому что точка в именах переменных
допустима не везде.

## Часть 8. Что осталось слабым

**Образы никуда не публикуются.** Их надо собирать у себя; готового `docker pull` нет. Для этого
нужны реестр и сборка в CI.

**Нет обратного прокси и TLS.** Система рассчитывает, что кто-то поставит его перед ней.

**Нет ограничений ресурсов.** Контейнер без `mem_limit` может съесть память хоста.

**Нет резервного копирования базы.** Том живёт, пока его не удалят; регламента снятия копий нет.

**Установка агента ручная.** Скрипт установки и юнит systemd были бы следующим шагом.

---

## Что запомнить из главы

- Контейнер описывает окружение кодом; «работает у меня» — свойство машины, а не программы.
- В многоступенчатой сборке компилятор остаётся на первом этапе и в образ не попадает.
- Копируй сначала то, что меняется редко: кэш слоёв экономит время каждой сборки.
- Спрашивай, **чьё окружение** измеряет инструмент: агент в контейнере измерит контейнер.
- «Контейнер запущен» и «сервис готов» — разные события.
- Миграции при старте хороши для одного экземпляра и опасны для нескольких.
- Проверка здоровья не требует секрета и не раскрывает подробностей.
