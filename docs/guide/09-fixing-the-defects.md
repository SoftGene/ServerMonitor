# Глава 09 — Работа над ошибками

Написание глав 00–08 неожиданно превратилось в аудит: чтобы объяснить каждое решение,
пришлось его обосновать, — и всё, чему обоснования не нашлось, всплыло само. Набралось около
пятнадцати дефектов, от опечаток до настоящей дыры в безопасности.

Эта глава — разбор каждого исправления: что было, почему это плохо, как стало и какое правило
из этого следует. Читать её полезно после остальных: здесь много ссылок на них.

> **Наблюдение, которое стоит унести отдельно.** Обычное code review проверяет код на
> соответствие ожиданиям. Объяснение кода новичку требует **обосновать сами ожидания** — и
> необоснованное обнажается. Если хочешь найти в своём проекте то, что не находится глазами,
> попробуй написать про него учебник.

## Часть 1. Безопасность

### 1.1. Пароль от базы в репозитории

**Было.** Строка подключения вместе с паролем лежала в `ServerMonitor.Api/appsettings.json`,
а этот файл отслеживается git.

**Чем плохо.** Проект задуман как портфолио, то есть рано или поздно станет публичным. Пароль
попал бы в открытый доступ — причём не только в текущем файле, но и **во всей истории
коммитов**, откуда обычным редактированием он не убирается.

**Стало.** Строка перенесена в User Secrets (глава 08), в файле остался пустой шаблон, а
`Program.cs` проверяет настройку при старте:

```csharp
if (string.IsNullOrWhiteSpace(connectionString))
{
    throw new InvalidOperationException("Connection string 'DefaultConnection' is not configured. ...");
}
```

**Что осталось сделать руками.** Старый пароль уже в истории — его нужно **сменить в самой
базе**. Технически историю можно переписать (`git filter-repo`), но это меняет хеши всех
коммитов; для одиночного проекта проще считать пароль скомпрометированным и заменить.

> **Правило.** Секрет, попавший в систему контроля версий, считается раскрытым навсегда.
> Удаление файла его не спасает — спасает только смена секрета.

**Заодно про `fail fast`.** Проверка при старте — не формальность. Без неё приложение
запустилось бы и падало на каждом обращении к базе с невнятной сетевой ошибкой. Лучше не
стартовать вовсе, но с сообщением, которое прямо говорит, что делать.

### 1.2. Бот отвечал любому

**Было.** Обработчик команд отправлял ответ на `message.Chat.Id` — то есть тому, кто написал.
Проверки, что это разрешённый чат, не было.

**Чем плохо.** Любой, кто узнал бы имя бота, отправлял `/status` и получал загрузку
процессора, объём памяти и заполненность диска сервера. Для подготовки атаки это ценные
сведения — например, видно, когда машина под нагрузкой и хуже отвечает.

**Стало.** Команды от посторонних чатов игнорируются:

```csharp
if (!string.Equals(message.Chat.Id.ToString(), _chatId, StringComparison.Ordinal))
{
    _logger.LogWarning("Ignored command from unauthorized chat {ChatId}.", message.Chat.Id);
    return;
}
```

Обрати внимание на `LogWarning`: игнорировать чужие команды молча — значит не узнать, что
бота кто-то нашёл.

> **Правило.** Идентификатор отправителя из входящего сообщения — это **не** авторизация.
> Всегда сверяй его с тем, кому ты действительно готов отвечать.

## Часть 2. Корректность

### 2.1. Разбор чисел без указания культуры

**Было.** В разборе `/proc/uptime`:

```csharp
snapshot.UptimeSeconds = double.Parse(parts[0]);
```

**Чем плохо.** `double.Parse` без второго аргумента использует культуру текущего потока.
Содержимое `/proc` — машинный формат с **точкой** в роли разделителя дробной части. В русской
культуре разделителем считается запятая, и строка `"348915.42"` вызвала бы `FormatException`.

Ошибка латентная: на Windows этот код не выполняется, а у служб на Linux обычно инвариантная
культура. Но `LANG=ru_RU.UTF-8` — и сбор метрик начал бы падать каждые несколько секунд.

**Стало.** Везде явная инвариантная культура:

```csharp
return double.Parse(parts[0], CultureInfo.InvariantCulture);
```

**Это уже второй случай в проекте.** Первый был зеркальным: при **форматировании** ширины
прогресс-бара получалось `width: 4,63%`, и браузер такое значение игнорировал (глава 01).
Тогда ломалось формирование строки, теперь ломался бы разбор.

> **Правило.** Всё, что читает или пишет машина — CSS, JSON, SQL, URL, файлы `/proc`, —
> обрабатывай через `CultureInfo.InvariantCulture`. Культура пользователя нужна только для
> того, что читает человек.

На этот случай написан регрессионный тест, который подменяет культуру потока и проверяет
разбор:

```csharp
Thread.CurrentThread.CurrentCulture = new CultureInfo("ru-RU");
var seconds = ProcParser.ParseUptimeSeconds("348915.42 2712334.11");
Assert.Equal(348915.42, seconds, precision: 2);
```

### 2.2. Загрузка процессора в Windows

**Было.** Перебор всех процессов системы с суммированием их процессорного времени, дважды за
замер, с пустым `catch {}` для процессов, к которым нет доступа.

**Чем плохо.** Три проблемы разом: систематическое занижение (время недоступных процессов не
учитывалось), заметная стоимость (200–400 объектов на каждый замер) и молчаливое
проглатывание исключений.

**Стало.** Системный вызов `GetSystemTimes` — прямой аналог `/proc/stat` (глава 05).

Побочный выигрыш оказался важнее основного: счётчики Windows и Linux устроены одинаково, и
теперь **обе платформы считают загрузку одной и той же функцией**
`ProcParser.CalculateCpuUsagePercent`. Формула существует в единственном экземпляре, и тесты
на неё покрывают сразу обе системы.

> **Правило.** Когда одну и ту же величину считают два платформенных пути, стоит поискать
> способ свести их к общей функции. Обычно он есть, и находится он на уровне данных, а не
> кода: как только счётчики привели к одному виду, различия исчезли.

### 2.3. «Первый попавшийся» диск

**Было.** В Windows брался первый готовый диск из списка.

**Чем плохо.** Лотерея: обычно `C:`, но подключённый образ или карта памяти с меньшей буквой
увели бы метрику на себя. Мониторинг показывал бы заполненность не того тома, и никто бы
этого не заметил — числа выглядят правдоподобно.

**Стало.** Берётся раздел, на котором стоит система:
`Path.GetPathRoot(Environment.SystemDirectory)`.

> **Правило.** «Обычно правильный» выбор в мониторинге хуже явной ошибки: неверное число
> выглядит как верное.

### 2.4. `async void` без обработки исключений

**Было.** Обработчик события навигации в `TopNav`:

```csharp
private async void OnLocationChanged(object? sender, EventArgs e)
{
    await JS.InvokeVoidAsync("navPill.update");
    await InvokeAsync(StateHasChanged);
}
```

**Чем плохо.** У `async void` нет `Task`, а значит некому поймать исключение: оно уходит прямо
в среду выполнения и может уронить процесс (глава 01). Здесь `async void` оправдан — сигнатура
обработчика события требует именно `void`, — но тогда ловить исключения обязан сам метод.

**Стало.** Тело обёрнуто в `try/catch`, а обращение к JavaScript вынесено в отдельный метод,
где отдельно обрабатывается `JSDisconnectedException` — штатная ситуация, когда соединение с
браузером уже закрыто и обновлять просто нечего.

> **Правило.** `async void` допустим только в обработчиках событий, и только с `try/catch`
> внутри. Ожидаемые исключения (разрыв соединения) стоит ловить отдельно от неожиданных: их не
> нужно логировать как ошибки.

### 2.5. Обращения по индексу без проверок

**Было.** `lines[0]`, `parts[7]`, `parts[1]` — разбор полагался на то, что файл имеет
ожидаемый вид.

**Стало.** Проверки длины и понятные сообщения:

```csharp
if (parts.Length < 8 || !parts[0].StartsWith("cpu", StringComparison.Ordinal))
{
    throw new FormatException($"/proc/stat cpu line has an unexpected format: '{statLine.Trim()}'.");
}
```

Разница видна в журнале: вместо `IndexOutOfRangeException` без контекста — сообщение с самой
проблемной строкой.

> **Правило.** Разбирая внешний формат, считай его недоверенным. Ошибка должна называть, что
> именно не так, — тебе же читать этот журнал в три часа ночи.

## Часть 3. Данные и производительность

### 3.1. Индексы

**Было.** Единственный индекс — первичный ключ по `Id`, при том что каждый запрос проекта
сортирует по `TimestampUtc`.

**Стало.** `HasIndex` в `OnModelCreating` и миграция `AddTimestampIndexes` для обеих таблиц
(глава 03).

> **Правило.** Колонка, по которой ты сортируешь или фильтруешь в горячем запросе, почти
> всегда должна быть проиндексирована. Проверяется командой `EXPLAIN`: `Seq Scan` в плане
> запроса по большой таблице — сигнал.

### 3.2. `AsNoTracking` и асинхронные вызовы

**Было.** Запросы только на чтение возвращали отслеживаемые сущности; в боте встречался
синхронный `FirstOrDefault()`.

**Стало.** `AsNoTracking()` во всех читающих запросах, `...Async` с передачей токена везде.

Выигрыш здесь микроскопический — и это нормально. Смысл не в производительности, а в
единообразии: когда весь код написан в одном стиле, отклонение сразу заметно и становится
поводом задуматься.

## Часть 4. Чистота кода

### 4.1. Удаление неиспользуемого эндпоинта

`GET /api/metrics/latest` отдавал наружу сущность базы данных (глава 02) — и при этом его
никто не вызывал.

Выбор был между «завести DTO» и «удалить». Выбрали удалить: всё, что он умел, покрывает
`/status`, а неиспользуемый публичный эндпоинт — это лишняя поверхность API, которую нужно
поддерживать и защищать.

> **Правило.** Мёртвый код не бесплатен: его читают, поддерживают и защищают. Если
> функциональность дублируется — удаляй, git помнит.

### 4.2. Вычисляемые свойства и почему они не всегда работают

**Было.** Формула процента памяти жила в двух местах: в контроллере и в боте.

**Стало.** Вычисляемые свойства на сущности:

```csharp
public double MemoryUsagePercent =>
    MemoryTotalMb > 0 ? Math.Round(MemoryUsedMb / MemoryTotalMb * 100, 1) : 0;
```

и явное `Ignore` в модели EF Core, чтобы для них не искались колонки.

**А вот и тонкость, ради которой стоит читать этот раздел.** Заменить формулу **везде** не
получилось:

```csharp
// работает: latest — обычный объект в памяти
MemoryUsagePercent = latest.MemoryUsagePercent

// НЕ работает: проекция выполняется на стороне PostgreSQL
.Select(m => new MetricHistoryItemDto { MemoryUsagePercent = m.MemoryUsagePercent })
```

Во втором случае EF Core строит SQL из дерева выражений (глава 03) и не может перевести
вычисляемое свойство C# в SQL — запрос упал бы с ошибкой трансляции. Поэтому в запросах
истории деление осталось написанным вручную, с комментарием, объясняющим почему.

> **Правило.** Граница «выполняется в базе» / «выполняется в памяти» определяет, каким кодом
> можно пользоваться. Внутри `Select`, уходящего в SQL, доступно только то, что провайдер
> умеет перевести.

Полностью убрать это дублирование можно было бы вычисляемой колонкой в самой базе — но тогда
формула переехала бы в миграцию, то есть в другую технологию. Для учебного проекта
двух-строчное повторение с комментарием честнее.

### 4.3. Перечисления вместо строк

**Было.** `MetricType` и `AlertType` — строки, в коде литералы `"CPU"`, `"Triggered"`.

**Чем плохо.** Опечатку `"Trigered"` компилятор не остановит, а фронтенд сравнивает именно со
строкой — интерфейс молча покажет не тот цвет.

**Стало.** Перечисления `MetricKind` и `AlertKind`, а в базе — по-прежнему строки, благодаря
**конвертеру значений**:

```csharp
entity.Property(a => a.MetricType)
    .HasConversion(
        kind => kind.ToDisplayName(),
        value => Enum.Parse<MetricKind>(value, ignoreCase: true));
```

Две лямбды описывают перевод в обе стороны. Благодаря этому:

- старые записи читаются без миграции данных;
- контракт API не изменился — наружу уходят те же строки;
- в коде появилась проверка компилятором.

> **Правило.** Переход на перечисления не обязан ломать хранилище. Конвертер значений
> позволяет изменить представление в коде, оставив данные как есть, — и это лучший тип
> рефакторинга: выигрыш есть, риска нет.

### 4.4. Настройки вместо констант

Интервал сбора (5 секунд), интервал проверки порогов (30 секунд) и число подтверждающих
замеров вынесены в секцию `Monitoring` и читаются через `IOptions<MonitoringOptions>`
(глава 08).

Заодно в классе настроек появились удобные свойства с защитой от бессмыслицы:

```csharp
public TimeSpan CollectInterval => TimeSpan.FromSeconds(Math.Max(1, CollectIntervalSeconds));
```

`Math.Max(1, ...)` не даст превратить опечатку в конфигурации (ноль или отрицательное число) в
бесконечный цикл без пауз.

## Часть 5. Надёжность алертинга

### 5.1. Состояние переживает перезапуск

**Было.** Три поля `_cpuWasHigh`, `_memoryWasHigh`, `_diskWasHigh` в памяти сервиса.

**Чем плохо.** Перезапуск во время аварии — повторное сообщение о том, о чём уже сообщали.
Перезапуск после того, как нагрузка спала, — «восстановление» не приходит вовсе.

**Стало.** При старте состояние восстанавливается из таблицы `Alerts`: последняя запись по
метрике и есть её текущее состояние (глава 07).

> **Правило.** Прежде чем заводить новое хранилище состояния, посмотри — возможно, оно уже
> выводится из тех данных, что у тебя есть.

### 5.2. Подтверждение длительностью

**Было.** Решение принималось по одному последнему замеру.

**Чем плохо.** На дёрганой метрике у порога — цепочка Alert → Recovered → Alert →
Recovered, то самое «дребезжание».

**Стало.** Тревога поднимается только после N подряд идущих превышений (по умолчанию три, то
есть полторы минуты при интервале 30 секунд).

Осталась несделанной вторая половина классического рецепта — **разные пороги на срабатывание
и восстановление**. Она требует второго порога в настройках и на странице Settings, поэтому
отложена до этапа доработки алертинга.

### 5.3. Словарь состояний вместо делегатов

**Было.** Состояние трёх метрик передавалось в метод проверки **парой делегатов** — «прочитать
поле» и «записать поле» (`Func<bool>` и `Action<bool>`, глава 01).

**Стало.** Словарь `Dictionary<MetricKind, MetricAlertState>` и объект состояния с двумя
полями.

Сравни сигнатуры:

```csharp
// было
private async Task CheckThreshold(AppDbContext dbContext, double value, double threshold, string name,
    Func<bool> getWasHigh, Action<bool> setWasHigh, CancellationToken cancellationToken)

// стало
private async Task CheckThresholdAsync(AppDbContext dbContext, MetricKind kind, double value,
    double threshold, CancellationToken cancellationToken)
```

> **Правило.** Делегаты в параметрах — мощный инструмент, но если они появились только чтобы
> обойти неудобное хранение состояния, лечить надо хранение. Признак: параметров становится
> больше, а читаемость падает.

## Часть 6. Тесты

### Рефакторинг ради тестируемости

Тестов не было вовсе, и написать их «как есть» не получилось бы: разбор `/proc` был
перемешан с чтением файлов, а значит требовал настоящего Linux.

Поэтому разбор вынесли в класс `ProcParser` — **чистые функции**: на вход строка, на выходе
число, никаких обращений вовне. Такие функции тестируются тривиально:

```csharp
[Fact]
public void ParseCpuTimes_SumsAllStatesIntoTotal()
{
    var times = ProcParser.ParseCpuTimes("cpu  100 20 30 500 40 5 5 0 0 0");

    Assert.Equal(540, times.Idle);   // idle + iowait
    Assert.Equal(700, times.Total);
}
```

> **Правило.** Если код трудно протестировать — обычно проблема не в тестах, а в том, что
> вычисления смешаны с вводом-выводом. Разделив их, получаешь тестируемость бесплатно.

### Что тестировать в первую очередь

Написано 25 тестов, и они целятся в три категории:

1. **Разбор внешних форматов** — ломается первым при обновлении системы: `/proc/meminfo`,
   `/proc/uptime`, `/proc/stat`, включая повреждённые данные.
2. **Формулы** — вычисление загрузки: обычный случай, нулевая дельта, счётчики пошли назад,
   защита от целочисленного деления.
3. **Регрессии на уже случившиеся ошибки** — тест с подменой культуры существует именно
   потому, что эта ошибка была допущена.

Третья категория самая ценная: **каждый найденный баг стоит закрывать тестом**, иначе он
вернётся.

### Один тест, который здесь не запускается

Два теста запускают настоящий сбор метрик. На этой машине они падают — но не из-за кода:
Windows Smart App Control блокирует загрузку свежесобранной неподписанной сборки из папки
тестов (ошибка `0x800711C7`).

Красный набор тестов хуже, чем отсутствующий: на него перестают смотреть. Поэтому такие тесты
сделаны **явно включаемыми**:

```csharp
public sealed class LocalCollectorFactAttribute : FactAttribute
{
    public LocalCollectorFactAttribute()
    {
        if (Environment.GetEnvironmentVariable("SERVERMONITOR_RUN_COLLECTOR_TESTS") != "1")
        {
            Skip = "Установи SERVERMONITOR_RUN_COLLECTOR_TESTS=1, чтобы запустить тесты реального сбора метрик.";
        }
    }
}
```

Запустить их можно так:

```bash
SERVERMONITOR_RUN_COLLECTOR_TESTS=1 dotnet test
```

> **Правило.** Тест, который не может пройти в данном окружении, нужно **пропускать явно и с
> объяснением**, а не оставлять красным и не удалять. Пропуск с причиной — это документация;
> красный тест — это шум.

## Что запомнить из главы

- Секрет, попавший в git, считается раскрытым: меняй сам секрет, а не файл.
- Идентификатор из входящего сообщения — не авторизация.
- Инвариантная культура — для всего, что читает и пишет машина; культура пользователя — только
  для человека.
- Неверное число в мониторинге опаснее явной ошибки: оно выглядит правдоподобно.
- `async void` разрешён только в обработчиках событий и только с `try/catch`.
- Граница «SQL / память» определяет, какой код можно использовать внутри запроса.
- Конвертер значений EF Core позволяет менять представление в коде, не трогая данные.
- Прежде чем заводить хранилище состояния — проверь, не выводится ли оно из имеющихся данных.
- Трудно тестировать — значит, вычисления смешаны с вводом-выводом; разделяй.
- Каждый найденный баг закрывай тестом, иначе он вернётся.

Дальше гайд растёт вместе с проектом: следующие главы — агент и мульти-сервер, heartbeat,
аутентификация, срок хранения данных.
